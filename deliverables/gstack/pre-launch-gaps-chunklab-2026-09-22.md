## 六、追加：B3（`best` LWW）判定 —— **是真缺陷，非「既定语义」**

方法：用**出厂真实纯函数**（`js/core-merge.js` + `js/core-sync-kv.js`）跑场景对照，不改业务文件。
脚本 `.workbuddy/_audit/best-lww-defect.mjs` → 结果 `best-lww-defect.txt`。

### 机制（读码 + 实测）

`best ∈ SYNC_KV_KEYS`（`core.js:107` = `['best','stats','settings']`）⇒ 走两条**互斥**分支
（`src/core/sync-kv-merge.mjs:47-55`，`core.js:3332-3334` 内联镜像同形）：

```
① rRev === lRev 且内容不同  →  mergeBest(本地, 远端)   ← 并集，安全
② rRev >  lRev              →  mem[key] = remote[key]  ← 整块替换，不做任何合并
```

`mergeBest`（`core.js:621-645` / `CoreMerge.best`）确为**并集**：两侧 key 取并、逐 deck 取 max。
⇒ **问题不在 `mergeBest`，而在它只在 rev 严格相等时才被调用。**

### 实测（真实函数）

| 场景 | 本地独有 `best['builtin-daily']` |
| --- | --- |
| `lRev = rRev = 1`（并发同版本） | **保留** ✅（并集生效） |
| `lRev = 1, rRev = 2`（他机已上行、本机未上行） | **被丢弃** ❌（静默） |
| `lRev = 0, rRev = 1`（旧版本无 rev 记录 = 升级路径） | **被丢弃** ❌ ← **正是 `upgrade-check` 观察到的现象** |
| 远端 `best === undefined`（新账号首同步） | 保留 ✅（不触发该分支） |

### 判定：**真缺陷**，但非无条件触发

- **为什么是真缺陷**：`core.js:99-106` **自己**就把这种配置定性为
  「**留在 `SYNC_KV_KEYS` 里会退回 LWW 整块替换，那正是「本机未上行的改动被他机覆盖」的根因**」，
  并据此把 `mastered / reinforceBook / deletedItems` 移出到行表（并集 + 墓碑）。
  **`best` 没被移出 ⇒ 属同类问题的遗留。** 判据是项目自己的定性，不是我新加的。
- **触发条件（三条同时成立）**：① 本地有 `best` 记录；② 云端已有 `best`（`rev ≥ 1`）；
  ③ **首次同步前 `revs.kv.best` 未初始化**。
- **为什么 ③ 会成立**：`revs.kv.best` 只在 `saveMem → maintainRevs` 里被置 1
  （`revision-delta.mjs:63-65` / `core.js:229`）；而 `loadMem` **仅在「发生了迁移」时**才 `saveMem`
  （`core.js:824-851`）⇒ **不需要迁移的用户，启动同步前可能一次 `saveMem` 都没有**。
- ⚠️ **仍是推断（未端到端复现）**：我**没有**跑「真浏览器 + 真 IDB + 真服务端」的端到端复现，
  所以「生产里有多少用户真会踩到」**未量化**。机制层面已可判定为缺陷；影响面需再测。
