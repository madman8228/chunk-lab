# 进度确认后的目录重复请求优化

## 现象与复现

`LearningWorkspaceRuntime` 在可见工作区收到 `server-cache-applied` 时调用完整刷新。首页每次因此读取 `/api/personal-wordbooks`；发现页还读取 `/api/library`。这些远程目录独立于已确认的进度缓存，不需要跟随每次进度投影重新读取。

新增 `scripts/workspace-cache-request-budget.test.cjs`，在新建 VM 环境加载真实运行时，使用虚拟账号和内存缓存。修改前：首页初始化后派发五次确认事件，断言失败 `6 !== 1`，即额外五次目录请求。没有读取或修改真实账号、课程、浏览器数据。

## 根因与系统性处理

本地投影刷新与远程目录刷新共用了入口。原有并发合并只能合并同时发生的任务，无法避免顺序确认事件产生的无关网络读取。

在前端运行时区分本地确认刷新与完整刷新：已初始化的当前视图收到确认事件时，仍读取已确认进度和待保存投影，但不重新请求独立目录。未初始化视图／账号变化自动使用完整刷新。完整刷新在本地任务执行期间触发时会等待后继续执行，不会被吞掉。

保留页面切换、聚焦、恢复联网、个人单词本恢复及手动刷新的远程读取；不增加持久目录缓存、不改变服务端 API、账号权限或答题保存协议。远程错误提示及其退避重试不会被一次本地刷新抹除。

收益是消除与确认事件数量成比例的目录读取；代价是确认事件本身不再作为独立目录的隐式刷新触发器。目录更新仍通过上述完整刷新入口获得。本轮不承诺消除全部请求，也不据此推算一万日活容量。
